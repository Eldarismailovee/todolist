# Todo App

Full-stack приложение для задач: FastAPI (async), SQLAlchemy 2.0,
PostgreSQL 16, Redis Pub/Sub и SSE на бэкенде; React 19 / Vite / TanStack Query
на фронтенде.

Возможности: канбан с drag-and-drop, редактор Tiptap с загрузкой картинок,
полнотекстовый поиск с тегами и категориями, дедлайны с уведомлениями на почту
и в Telegram, AI-помощник, графики продуктивности на Recharts. Вход — по паролю
с обязательным кодом из письма (OTP) либо через Google/GitHub.

## Запуск

```bash
docker compose up -d                 # PostgreSQL :55433, Redis :56379
uv sync
cp .env.example .env
uv run alembic upgrade head
uv run python -m app.cli seed-attributes
uv run python -m app.cli create-admin admin@example.com 'длинный-пароль'
uv run fastapi dev app/main.py       # http://127.0.0.1:8000/api/docs
uv run python -m app.worker          # напоминания о дедлайнах, отдельный процесс
```

Письма локально уходят в Mailpit — http://127.0.0.1:8026 (для этого задайте
`SMTP_HOST=127.0.0.1` и `SMTP_PORT=1026`); без `SMTP_HOST` они просто пишутся
в лог. Без ключей OAuth, Telegram и Anthropic соответствующие
функции честно выключаются или работают в режиме заглушки — приложение при этом
полностью работоспособно.

В соседнем терминале — SPA:

```bash
cd frontend
npm install
npm run dev                          # http://localhost:5173
```

Vite проксирует `/api` на бэкенд, поэтому SPA и API живут на одном origin:
иначе cookie сессии с `SameSite=Strict` и точная проверка `Origin` не
работают. `ALLOWED_ORIGIN` в `.env` должен совпадать с адресом Vite.

**Бэкенд должен быть запущен**: без него прокси отвечает `502` с текстом
«Бэкенд http://127.0.0.1:8000 недоступен…», и этот текст виден в интерфейсе.
Адрес переопределяется переменной `BACKEND_URL`.

Порты в `docker-compose.yml` нестандартные (55433/56379/8026), потому что
стандартные на этой машине заняты другими проектами.

### Внешние сервисы

| Переменная | Что включает | Если не задана |
| --- | --- | --- |
| `GOOGLE_CLIENT_ID` / `_SECRET` | Кнопка «Войти через Google» | Кнопка не показывается |
| `GITHUB_CLIENT_ID` / `_SECRET` | Кнопка «Войти через GitHub» | Кнопка не показывается |
| `SMTP_HOST` и соседние | Отправка кодов и напоминаний | Письма пишутся в лог |
| `TELEGRAM_BOT_TOKEN` | Напоминания в Telegram | Сообщения пишутся в лог |
| `ANTHROPIC_API_KEY` | AI-помощник на Claude | Детерминированная заглушка, помеченная в интерфейсе |
| `SECRET_KEY` | Подпись OTP и ссылок на файлы | Значение по умолчанию + предупреждение в логе |

Redirect URI для обоих провайдеров: `{ORIGIN}/api/v1/auth/oauth/{provider}/callback`.

### Среда и проверка конфигурации

`ENVIRONMENT` принимает `development` (по умолчанию), `test` или `production`.
При `production` приложение **не стартует**, если конфигурация оставляет
локальные послабления: ключ по умолчанию или короче 32 символов,
`COOKIE_SECURE=false`, `OTP_LOG_CODES=true`, `ENABLE_TESTING_ENDPOINTS=true`,
пустой `SMTP_HOST` (вход завершается кодом из письма — без SMTP код уходит в
лог). Проверка живёт в `Settings`, поэтому одинаково работает для API, воркера
и CLI.

Логирование обоих процессов поднимается из `app/logging_config.py`: httpx на
INFO пишет URL каждого запроса, а у Telegram bot token лежит прямо в пути, так
что клиентские логгеры приглушены до WARNING.

## Тесты

```bash
timeout 900 uv run pytest -q         # 227 тестов
uv run ruff check app tests
```

Тесты работают с настоящими PostgreSQL и Redis (база `todo_test`, префикс
ключей `todo:test`) и поднимают **два процесса uvicorn** на портах 8099/8100:
действие сессии и Pub/Sub проверяются между разными воркерами, а не внутри
одного процесса.

Фронтенд:

```bash
cd frontend
npm run lint                         # ESLint 10
npm run format:check                 # Prettier
npm run test                         # Vitest, юнит-тесты
npm run build                        # tsc --noEmit + vite build
npm run e2e                          # Playwright, сквозной сценарий
```

Сквозные тесты требуют запущенных бэкенда (:8000) и Vite (:5173) и используют
системный Chromium (`CHROMIUM_PATH`), поэтому браузеры Playwright локально не
скачиваются. Код подтверждения тест не может «подсмотреть» — он хранится хешем;
для этого бэкенд поднимается с `ENABLE_TESTING_ENDPOINTS=true`, и только тогда
регистрируется служебный маршрут `/api/v1/testing/otp`. В production этого пути
не существует.

## Архитектурные решения

**Авторизация — серверная сессия в cookie.** Значение сессии — 256 бит
случайности; в базе лежит только SHA-256. Клиент получает его в
`HttpOnly; Secure; SameSite=Strict` cookie с `Path=/api/v1`, то есть она
покрывает все маршруты, включая SSE и выдачу картинок. Токенов в JavaScript
нет вовсе: читать XSS нечего, а отправить cookie куда-то ещё браузер не даст.

Сессия ограничена двумя сроками: абсолютным (активность его не продлевает) и
пределом простоя. Простой продлевается не чаще `SESSION_TOUCH_INTERVAL_SECONDS`,
иначе каждое чтение сессии было бы записью и блокировкой строки для остальных
параллельных запросов того же пользователя.

Прежняя схема выдавала одноразовый access token и меняла refresh перед каждым
защищённым запросом. Это добавляло round-trip и транзакцию с блокировками на
каждый вызов, выстраивало параллельные запросы в очередь под общим Web Lock и
создавало строку в БД на каждый обмен. Обмена больше нет: запрос стоит одного
чтения сессии. Сквозной сценарий в браузере после перехода идёт вдвое быстрее
(31,7 с → 15,4 с).

Отказ от ротации убирает и обнаружение повторного использования — обнаруживать
стало нечего. Защита сессии теперь держится на `HttpOnly`, `Secure`,
`SameSite=Strict`, коротком пределе простоя и немедленном отзыве, который
проверяется при каждом запросе.

**CSRF.** Cookie браузер прикладывает сам, поэтому проверка Origin и
обязательного заголовка `X-CSRF-Guard: 1` висит на всём `/api/v1` для всех
небезопасных методов, а не на отдельных маршрутах входа. Безопасные методы
пропускаются: их защищает `SameSite=Strict` у самой cookie.

**Авторитет состояния сессии — PostgreSQL.** `session_is_active()` открывает
собственную короткую сессию БД, поэтому SSE не удерживает SQL-соединение весь
срок потока. В потоке отзыв проверяется по таймеру
(`SSE_REVOCATION_CHECK_SECONDS`, по умолчанию 5 с) и дополнительно перед
отправкой каждого события.

**SSE.** `EventSourceResponse` сам следит за разрывом соединения и владеет
ASGI-каналом `receive`, поэтому в генераторе нет своего опроса
`request.is_disconnected()` — второй потребитель того же канала мог бы
перехватить сообщение о разрыве. Поток закрывается по `deadline =
min(expires_at - 15, now + 240)`; переподключение требует нового токена.
Подписки берут отдельный пул Redis: каждая занимает соединение целиком.

**Валидация атрибутов.** Схема строится по `TaskAttributeMeta` через
`create_model` со строгими типами и `extra="forbid"`, кэш — `lru_cache` по
содержимому метаданных. `"false"` и `0` не проходят как boolean, дата — только
существующая календарная `YYYY-MM-DD`, `null` необязательного поля
нормализуется в отсутствие ключа, обязательный boolean может быть `false`.
Форма динамических полей строится по тем же метаданным (`AttributeFields`):
обязательные поля видны в быстром создании задачи, все — в диалоге. Без этого
добавленное администратором обязательное поле делало создание задачи
невозможным: интерфейс не отправлял значение и не давал его ввести.

**Контракт документа.** `content` проверяется по списку узлов, атрибутов и
marks тех расширений, которые действительно включены в редакторе (StarterKit,
Image, Link; заголовки 2–3). Неизвестный узел, лишний атрибут, `javascript:`
или `data:` в `href`/`src` отвергаются с `loc = ["body", "content"]`. Ограничений
глубины и числа узлов для этого недостаточно: они не задают, что именно
допустимо. Набор проверен против JSON настоящей схемы редактора, а не против
предположений о ней (`tests/test_content.py`).

**Момент времени.** `due_at` принимается только как ISO-строка с часовым
поясом (`AwareDatetime`). Значение без зоны истолковала бы БД, а число Pydantic
принял бы за Unix timestamp и молча подставил UTC.

**Смысл `null`.** В `PATCH /tasks/{id}` явный `null` допустим там, где очистка
значения — операция: описание, содержимое, срок, колонка, категория. Для
заголовка, тегов, атрибутов и признака выполнения `null` отвергается: раньше он
молча игнорировался и выглядел как применённое изменение.

**Лимиты тела.** `MaxBodySizeMiddleware` считает фактически прочитанные байты,
а не только `Content-Length`, поэтому chunked-запрос без заголовка тоже
обрывается. Лимит зависит от маршрута: `POST /api/v1/files` получает
`max_upload_bytes` плюс запас на обвязку multipart, остальные — общий
`max_request_body_bytes`. Один лимит на всё приложение не работает: по меньшему
значению объявленные 5 МиБ загрузки отвергались бы до маршрута, по большему
исчезла бы защита от произвольного JSON. `Settings` не поднимается, если общий
лимит меньше суммы полевых (`max_content_bytes` + `max_attributes_bytes` +
запас): иначе обещанный размер содержимого недостижим и вместо 422 приходит 413.

**Идемпотентность.** `POST /tasks` принимает `Idempotency-Key`: запись в Redis
привязана к владельцу и хешу тела, тот же ключ с другим телом даёт 409,
неудачная попытка освобождает ключ.

**Фронтенд.** `api` — обычный axios с `withCredentials`: никаких токенов,
перехватчиков выдачи и блокировок между вкладками. Выход рассылается остальным
вкладкам через BroadcastChannel.

Отказы разделены по видам (`classifyError`): 401 — сессии нет,
429 и 5xx — сервер жив и отказал временно, отсутствие ответа — результат
операции неизвестен. Завершённой сессию считает только 401; раньше любой сбой
обмена превращался в «войдите снова», и перегрузка сервера или пропавшая связь
выглядели как потерянный вход. Отдельно выделен 401 на маршрутах входа: там он
означает «неверный код или пароль», а не «сессия закончилась».

Выход, на который не пришёл ответ, показывается как неподтверждённый: локально
состояние очищено, но сессия могла уцелеть, и молчать об этом нельзя.

Типы берутся из OpenAPI (`npm run gen:api` → `src/api/schema.d.ts`), а не
пишутся руками: расхождение контракта ломает сборку, а не рантайм.

**Разделение бандла.** Recharts и Tiptap грузятся отдельными чанками через
`React.lazy`: на экране входа они не нужны, а вместе весили больше, чем всё
остальное приложение. Основной чанк — 486 КБ вместо 1.2 МБ.

**Сроки жизни credentials** заданы по назначению, а не одним числом: сессия
12 ч абсолютно и 1 ч простоя, OTP 600 с, OAuth `state` 300 с. Границы каждого
срока объявлены в `Settings` через `Field`, чтобы окружение не могло тихо
превратить короткий срок в долгий. Утверждение «все токены живут пять минут»
неверно и никогда не было верным: у кода из письма и у сессии разные задачи.

**Ограничение попыток** есть и у проверок пароля из авторизованной сессии
(смена пароля, удаление аккаунта) — свой счётчик на пользователя. Лимиты входа
по IP такие попытки не считают.

**Одноразовые коды.** Шестизначное значение слишком мало для обычного хеша:
в базе лежит HMAC-SHA256 с `SECRET_KEY`, попытки считаются, код одноразовый и
живёт 10 минут. Пароль сам по себе сессию не создаёт — `/auth/login` отвечает
`202`, а сессия появляется только после `/auth/otp/verify`.

**OAuth.** Секрет клиента и обмен кода живут на сервере; `state` гасится
атомарно через `GETDEL`, поэтому ссылка-возврат не срабатывает дважды. Для
Google дополнительно используется PKCE. Связать внешний аккаунт с существующим
можно только по адресу, подтверждённому провайдером: у GitHub для этого всегда
запрашивается `/user/emails`, потому что адрес в профиле может быть
неподтверждённым.

**Порядок при перетаскивании.** Позиция — `float`, элемент встаёт посередине
между соседями, поэтому перемещение меняет одну строку, а не весь список. Когда
зазор исчерпан (`position_between` возвращает `None`), колонка перенумеровывается
под блокировкой и вставка повторяется. Все операции порядка внутри проекта —
создание задачи и колонки, перемещение, перенумерация, удаление колонки —
сериализуются рекомендательной блокировкой транзакции
(`board_service.lock_project_board`): соседи читаются, позиция считается и
пишется разными запросами, и без общего замка два перемещения выбирают одно
значение, а два удаления проходят проверку «остаётся хотя бы одна колонка»
каждое по своему снимку. Соседи проверяются на самоссылку, совпадение
`before_id` и `after_id` и порядок.

**Признак выполнения** задаётся одним правилом (`board_service.apply_column_change`):
задача выполнена, пока лежит в колонке «готово»; любая другая колонка и «без
колонки» открывают её снова. Раньше PATCH и move давали разные состояния для
одного и того же действия. Явный `completed` применяется после колонки.

**Конкурентное редактирование.** Ответ задачи несёт `version`; клиент
возвращает его в `If-Match`, и правка по устаревшему снимку получает 412 вместо
молчаливого затирания изменения из другой вкладки. Гонку между чтением и
записью внутри запроса ловит `version_id_col` SQLAlchemy: UPDATE не находит
строку ожидаемой версии, и ответ — 409. Без заголовка проверки нет, старые
клиенты работают как прежде.

**Картинки в редакторе.** В документе хранится «голый» путь
`/api/v1/files/{id}`, и тег `<img>` открывает его той же сессионной cookie, что
и остальные запросы. Подписанных ссылок больше нет: они существовали только
потому, что `<img>` не мог отправить `Authorization`, и были предъявительским
доступом к файлу на час независимо от сессии. Выдача проверяет владельца по
сессии, а ссылка на чужой файл отвергается ещё на записи документа.

**Полнотекстовый поиск.** `search_vector` — генерируемая СУБД колонка
(`tsvector` с весами A/B/C по заголовку, описанию и тексту документа) с
GIN-индексом: значение не может разойтись со строкой. Пользовательский ввод
идёт через `websearch_to_tsquery`, поэтому кавычки и `-` не требуют
экранирования.

**Уведомления.** Воркер отдельный процесс; отметка об отправке уникальна по
`(task_id, kind)`, поэтому напоминание не уходит дважды даже при нескольких
воркерах.

## CI/CD и деплой

`.github/workflows/ci.yml` на каждый pull request прогоняет пять задач: бэкенд
(ruff + миграции + pytest на настоящих PostgreSQL и Redis), контракт (см. ниже),
фронтенд (ESLint, Prettier, Vitest, сборка), сборку образа API без публикации и
сквозные тесты в Chromium.

Контракт проверяется от исходников, а не сравнением двух checked-in файлов:
задача выгружает OpenAPI из текущего кода (`uv run python -m app.cli
export-openapi`), генерирует из него типы (`npm run gen:api`) и требует, чтобы
`openapi.json` и `frontend/src/api/schema.d.ts` в репозитории совпали с
результатом. Выгрузка принудительно отключает `ENABLE_TESTING_ENDPOINTS`:
служебных маршрутов нет в production, значит их нет и в контракте, а локальный
`.env` разработчика на результат не влияет.

Выкладка живёт в том же workflow: задачи `deploy-spa` (Vercel,
`frontend/vercel.json`) и `deploy-api` (образ в GHCR) идут через
`needs: [backend, frontend, contract, image, e2e]` и только на push в `main`.
Отдельного `deploy.yml` больше нет — он запускался по тому же push независимо
от проверок и мог выложить непрошедший CI код.

**Бэкенд нельзя развернуть на Vercel.** SSE держит соединение минутами, а
подписчик Redis Pub/Sub должен жить между запросами — serverless-функции этого
не позволяют. Поэтому SPA идёт на Vercel, а API — в контейнер (`Dockerfile`) на
Fly/Railway/VPS; `vercel.json` проксирует `/api` на этот хост, сохраняя единый
origin, без которого не работают cookie с `SameSite=Strict`. Миграции и воркер
напоминаний запускаются отдельными командами.

## Ограничения и что осталось

- **Vercel не может держать бэкенд** — причина в SSE и подписчике Redis, см.
  раздел выше. Это не обходится настройкой: нужен контейнерный хостинг.
- **Служебный маршрут `/api/v1/testing/otp`** отдаёт последний код
  подтверждения. Он подключается только при `ENABLE_TESTING_ENDPOINTS=true`;
  при `ENVIRONMENT=production` этот флаг не даёт приложению стартовать.
- **`SECRET_KEY` по умолчанию** подписывает OTP и ссылки на файлы известным
  значением. Вне production это предупреждение в логе, в production — отказ
  старта.

## Что не сделано

- **Фоновая сверка** сделана простым `refetchInterval` (60 с) и refetch при
  возврате фокуса; отдельной логики сверки версий нет.
- **Экран администратора** для справочника атрибутов: правка через API
  (`/api/v1/admin/task-attributes`) и CLI, UI для неё не сделан.
- **Оптимистичные обновления** не используются: после мутации выполняется
  инвалидация, состояние приходит с сервера.
- **Фоновый экспорт.** Синхронный экспорт ограничен `EXPORT_MAX_TASKS` (5 000);
  выше порога возвращается 413. Порционная выгрузка со согласованным снимком и
  защищённой выдачей файла не реализована.
- **Transactional outbox.** Публикация после commit — «по возможности»:
  при падении процесса между commit и publish событие теряется, клиент узнает
  об изменении при следующем reconnect (`ready` → полная инвалидация) или
  фоновой сверке.
- **WebAuthn / Passkeys** — только заготовка в виде разделения auth-слоя.
**Подключение Telegram.** Введённый chat ID владением чатом не является: с
ним можно было бы подписать чужой чат на свои уведомления. Сервер отправляет
код подтверждения прямо в указанный чат (`POST /notifications/telegram/link`),
и доставка включается только после возврата кода
(`POST /notifications/telegram/confirm`). Прочитать код может лишь тот, у кого
есть доступ к чату. `PUT /notifications/settings` chat_id вообще не принимает,
а `telegram_enabled` без подтверждённого чата отвергается. Попытки ввода кода
ограничены, маршруты выдачи кода и проверки связи — по пользователю: каждый из
них отправляет сообщение в чат. Полноценная привязка через `/start <код>` у
самого бота потребовала бы приёма обновлений Telegram, которого в приложении
нет.

**Хранение записей сессий.** Строка живёт, пока сессию можно предъявить.
Воркер раз в час удаляет записи старше `session_retention_seconds` (по
умолчанию 7 суток) и пишет число удалённых в журнал — это единственная
имеющаяся метрика роста таблицы. Срок хранения не может быть меньше
абсолютного срока сессии: запись исчезала бы раньше, чем сессия перестанет
действовать.

**Тип загруженного файла** проверяется по сигнатуре формата, а не по заголовку
клиента: расширение на диске и Content-Type выдачи выбираются по заявленному
типу, поэтому расхождение означало бы выдачу произвольного содержимого под
видом картинки. Размеры изображения и стоимость декодирования не ограничены —
для этого нужен декодер, которого в зависимостях нет.

- **Уборка вложений.** Картинка, удалённая из текста задачи, остаётся на диске:
  сборщика осиротевших файлов нет. Удаление аккаунта свои файлы снимает,
  а неопределённый результат commit при загрузке оставляет файл и пишет его
  имя в журнал — БД и файловая система не образуют общей транзакции.
- **Хранилище вложений локальное.** Реплики API с разными дисками не увидят
  файлов друг друга. Для нескольких реплик нужен общий объектный store и явный
  жизненный цикл вложения (staged → ready → deleting) с повторяемой уборкой.
- **Перетаскивание с клавиатуры** работает через dnd-kit (`KeyboardSensor`), но
  отдельного экрана с объяснением сочетаний клавиш нет.
- **Ассистент без ключа** отвечает детерминированной заглушкой. Она помечена в
  интерфейсе и в поле `provider`, но полезной работы не делает.
- **Удаление аккаунта** удаляет строки в основной БД и байты вложений;
  обработка резервных копий и журналов требует отдельной политики хранения.
  Подтверждение — пароль, а для аккаунта без пароля (вход только через OAuth)
  одноразовый код на подтверждённый адрес: `POST /api/v1/user/delete-code`.
  Код привязан к действию и на `/auth/otp/verify` не принимается. Интерфейса
  для удаления пока нет, только API.
- **Регуляторные заявления.** Реализованы инженерные механизмы из раздела 4;
  утверждения о соответствии нормам ЕС не проверялись.

## Замечание к ТЗ

ТЗ требовало строго одноразовый access token с обменом refresh перед каждым
защищённым запросом. Это удваивало число round-trip'ов, сериализовало вкладки
под общим Web Lock и создавало строку в БД на каждый запрос, а любой сбой
обмена клиент был вынужден трактовать как конец сессии. Схема заменена на
серверную сессию в cookie: требование ТЗ в этой части не выполняется намеренно,
причины и последствия описаны выше в разделе «Авторизация».
